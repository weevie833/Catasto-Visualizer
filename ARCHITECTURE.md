# Catasto Visualizer Architecture

## Boundaries

- `index.html` and `index.css` hold the Visualizer page; its code is in `app.js` and the 3D view is started by `scene3d-boot.js`. No page contains inline script or style, so the server can send a strict Content-Security-Policy (`script-src 'self'; style-src 'self'`).
- `admin.html`, `admin.css`, and `admin.js` contain project-management workflows.
- `catasto-parser.js` is the only parser. Admin creates projects with it and the Visualizer reparses with it; name, place, residence, and neighbor-link rules for both languages are defined there. Its output carries `parser_version` (currently 9). A short standalone line naming a payee ("To the Chapel of the Rosary", "Alla Cappella del Rosario") is never a section heading. Excluded sections (non-resident owners, outside churches, the village's chapels) never become entries; their text is kept in `data.excluded_sections` (`heading`, `source_pages`, `source_page_breaks`, `source_entry`) for the Name Index only. Summary sections are not kept.
- `catasto-records.js` owns household records inside a project: permanent ids, repair of malformed imports, and carrying the user's edits across a reparse.
- `catasto-relations.js` builds the Adjacent Evidence report shown beside the source entry: a person's summary and associations by degree, with relations the entry states kept apart from relations derived from them, and family leads from other entries (households and married women of the same surname, ranked by neighbors, land borders, district, and age, with each clue shown). It also supplies the people a source entry names (`sourceEntryLinks`), which the Visualizer shows as links in the source text. It is computed from the loaded project on each selection and never saved; the plan is in `ADJACENT_EVIDENCE_PLAN.md`.
- `catasto-name-index.js` builds the Name Index / Indice Onomastico that Admin exports as JSON, CSV, or Markdown: every person a project names, with surnames derived from the household listing where the source omits them, and each person's village or city. It reads the stored source entries with the parser's helpers and `CatastoRelations.roleOf`, is loaded only by `admin.html`, and is never saved. It also reads `data.excluded_sections`: each owner line (a name with or without an origin, or one ending "possesses:"/"possiede:") is indexed under the place it names, and the people those sections name are read as references. The XLSX Index (`collectMentions` without `excludedSections`) follows the entries and leaves these sections out. The rules are in `NAME_INDEX_PLAN.md`.
- `catasto-xlsx-index.js` builds the XLSX Index that Admin exports from the same dialog: one row per person in the layout of the Customizable Transcriber's Catasto Onciario Index template, with ages, estimated birth years, occupations, parents, districts, and pages. It reads `CatastoNameIndex.collectMentions`; `catasto-xlsx.js` writes the file (one styled sheet, uncompressed ZIP). Both are loaded only by `admin.html`. The rules are in `XLSX_INDEX_PLAN.md`.
- On wide windows the 3D view and the text panels share the window height; the divider's position is kept in `localStorage` (`catasto-evidence-height`) as a display preference only.
- `scene3d.js` and `vendor/OrbitControls.js` import Three.js by relative path (`./vendor/three.module.js`, `./three.module.js`) instead of an import map, which the CSP would block. That one import line is the only change to the vendored files.
- A project's `data.source_language` (`en` or `it`) records which side of the transcription was parsed.
- `catasto-storage.js` owns the browser side of persistence and the portable exchange format; `project_store.py` owns the files, reached through `serve.py`'s `/api/`.
- User projects are JSON files, one per project, in a per-user folder outside the app: `%APPDATA%\Catasto Visualizer\projects\` on Windows, `~/Library/Application Support/Catasto Visualizer/projects/` on macOS, `$XDG_DATA_HOME/Catasto Visualizer/projects/` on Linux. Writes are atomic (temp file, then replace) and serialized by one lock. A save is reported only after it is on the disk, so it survives an OS crash or power loss (decision D11): each file is flushed before its rename (`F_FULLFSYNC` on macOS, `fsync` elsewhere), and the folder is flushed after every rename or removal. In a paired update, the staged files reach the disk before the transaction record, the record before the replacements, and the replacements before the record is removed; an import's files reach the disk before its journal is removed. Windows flushes file contents only; it cannot flush a folder. On macOS and Linux the folders are `0700` and the files `0600`, and files from earlier versions are tightened at startup; other accounts on the computer cannot read them. One trusted user runs the server; it has no per-launch token. The server takes an exclusive OS lock on `server.lock` in the data folder before any recovery, so a second server, on any port, stops without recovering or changing the running one's files. Stored JSON is standard JSON only: `NaN`, `Infinity` and numbers that overflow (such as `1e999`) are refused on input, in stored files and in replies, and page numbers must be integers a browser holds exactly (at most 2^53). A stored file that is not readable JSON is reported as damaged (500, with the file name) and left unchanged; the library list skips it.
- A project is limited to 50 MB; one import request may carry several projects, up to 200 MB.
- `GET /api/projects` returns summaries only (id, name, source file, timestamps, household count, language, snapshot date). A page fetches one project's full data when it opens it. The server parses a project or snapshot file only when it changed since the last listing (by modification time and size); the snapshot date shown is the `createdAt` recorded in the snapshot.
- A save that replaces both a project and its snapshot (an update or a restore) stages both files in `projects/.pending/`, records `transaction-<id>.json`, and only then replaces the real files. A failure before the record leaves both files as they were. Once recorded, the update is committed: any later read, save, delete, import, or listing of that project first finishes it, and the project is refused (503) while it cannot be finished, so a later save or delete is never overtaken by the earlier update. At startup, recorded transactions are finished and staged files without a record are discarded. A project whose update cannot be finished at startup does not stop the server: its record and staged files are kept, it is refused until a later attempt succeeds, and the library list marks it `unavailable` with the reason. Admin shows it without actions; the Visualizer lists it as "(being recovered)" and cannot open it.
- `GET /api/projects/<id>/export` returns the project and its previous version read together under the store lock, so an export cannot mix two saves.
- The server checks every household on every write (save, import, browser migration): each must be an object with a non-empty, unique `id` and a text `household_head`, and optional fields must have the types the app reads (`source_pages` numbers, `residence.adjacent_to` names, `residence_links` objects, text fields as text). The browser repairs imports to this shape first, and repairs old browser projects before copying them.
- A damaged `import-journal.json` is renamed `import-journal.damaged-<time>.json` at startup and no project is touched.
- Household source-entry edits and residence corrections are written directly to the active project file and are included in project exports.
- `/api/` refuses requests whose `Host` is not `127.0.0.1` or `localhost` at the server's port, and writes whose `Origin` is not that address or that do not send JSON, so other websites cannot read or change projects. Project ids are limited to `[A-Za-z0-9_-]` so they cannot name other files.
- `serve.py` checks the `Host` of every request, not only `/api/`, and serves only the app files listed in `APP_FILES`; transcriptions, backups, and other files kept in the app folder return 404. Responses carry `X-Content-Type-Options: nosniff`. Connections time out after 30 seconds of silence, at most 32 requests are handled at once, and a negative `Content-Length` is refused.
- Every save gives `updatedAt` a value later than the stored one, so the stale-save check holds even for two saves in the same millisecond.
- An import writes `import-journal.json` listing its projects before writing them and removes it when done. If the server stops part-way, the next start deletes the listed projects, which were all new, so an import is kept whole or not at all. If an import fails and removing what it wrote also fails, the journal is kept: its projects are refused (503) and listed `unavailable`, and every later access tries the removal again until it succeeds, so no change is saved to a project that recovery would remove. A new import is refused (503) while that journal remains, so it never replaces the journal of an import still being undone.
- The server code runs on Python 3.7 and later; `test_serve.py` checks that it parses under the 3.7 grammar.
- The repository contains no project data. A new installation starts with an empty library; source transcriptions and backups stay on the user's computer and are excluded by `.gitignore`.

## Upgrade Safety

Application updates may replace every app file without changing saved projects, because the project folder is outside the app folder and outside browser storage. Exported `.catasto.json` files provide backups and allow projects to move between users and computers.

Versions up to V 0.05 kept projects in the browser's IndexedDB (database `catasto-visualizer`, store `projects`). On first load, `catasto-storage.js` reads that store without changing it and sends its records to `/api/migrate`, then sets the `catasto-browser-projects-migrated` localStorage flag. The server adds only projects it does not have and has not copied before (`browser-migration.json` lists every copied id), so a project deleted after migration is never restored, and projects from several browsers are all kept. The IndexedDB copy is left as a fallback.

A save is refused when the stored project changed or was deleted after the saving tab loaded it, so one tab or window cannot silently overwrite another. A delete sends the loaded `updatedAt` too and is refused if the project was saved since, so a newer save is never discarded by a deletion confirmed against an older view. New projects are saved with `{ create: true }`.

Admin announces imports, creations, and deletions on the `catasto-projects` `BroadcastChannel`. Open Visualizer tabs reload their project list and open a newly imported or created project, unless a source edit or reparse review is open there, or a save is still in progress.

## Project Record

Each stored project contains an ID, display name, source filename, timestamps, and a parsed Catasto data object with a `households` array. Exchange files include an explicit format name and version; the current version is 2. A backup from a newer version is refused with a request to update the app.

Every new or imported project passes through `CatastoRecords.repairProjectData` and `convertToPermanentIds` (in `CatastoStorage.createProject`). Repair fills in missing optional fields silently, converts or removes values of the wrong type, takes a missing head from the first source line, and removes records with neither a head nor source text. Admin lists every change and asks before saving the import.

## Record IDs

Households have permanent random ids (`h-…`); `data.record_id_version` is 2. Names are display fields only, so renaming a head or reordering records never changes an id. Duplicate ids in an import are replaced, and links or decisions naming them are dropped and reported. Version 1 data, whose ids were slugs of the head's name, is converted once: at import, or when a stored project is opened. A conversion that keeps every link is saved at once; one that would drop links is shown as an update to review, and the previous data becomes the snapshot. Residence links, member identities, "keep separate" decisions and the record copies in merge history (both from earlier versions, which offered merging) are rewritten together. A reference to an id shared by several records cannot be resolved and is dropped; `data.record_id_migration.droppedReferences` lists each one, and the old id stays in `legacy_id`.

## Reparsing

Nothing is reparsed without the user's consent. When a project kept its transcription and its `parser_version` is older than the parser's, the Visualizer shows a notice. Review update shows the counts and a per-record list of changes (new, removed, residence place, neighbors added or removed) before anything is saved; Update project applies them.

- Exports place a name on its page by the page breaks the parser recorded (`source_page_breaks`). If a recorded break cannot be placed for certain (an edit changed a page's opening words so it is no longer found, the opening occurs more than once in the entry, or the openings are out of order), the whole entry is cited with all its pages rather than any text being moved to the wrong page.
- Merging households was removed on 2026-11-12; the app does not combine records. A record merged by an earlier version (it has `source_entries`) still claims every new entry whose text equals one of them, so an update does not split it. A merged entry found only by its head's name is an uncertain match, and the update is blocked; the remedy is to correct the source transcript and import it again. The Name Index and XLSX Index are refused for a project with a merged record (more than one `source_entries` item), because they read members from the first entry only; Admin names the households and disables the exports.
- Other new records are matched by identical source text, then by head name or alias in order, and keep the stored record's id.
- Records the user edited (`source_edited_at`, `residence_edited_at`) or merged by an earlier version (`source_entries`, `aliases`) keep their stored content. An edited record the new parse no longer finds is kept as it is. Unedited records the new parse no longer finds are removed.
- An unedited record keeps its stored residence place where the new parse reads it differently, because earlier versions applied residence corrections without marking them; the preview counts these.
- Page numbers taken only from a record's position are stored with `source_pages_inferred` and shown as "(inferred)".
- The update is blocked if the new project would exceed 50 MB.
- The previous data is saved as the project's snapshot in `projects/snapshots/<id>.json`, a separate private file that does not count toward the project's size, replacing any earlier snapshot. The old in-project `entryBoundaryMigrationBackup` is removed. Deleting a project deletes its snapshot.
- Admin's Restore previous version repairs a copy of the snapshot (a snapshot saved before the current record rules may not pass them), lists each repair in the confirmation, and sends the copy; the server checks it, makes it current, and keeps the replaced data as the new snapshot, so a restore can be undone. Download previous version saves the snapshot exactly as stored, as a project file Admin can import.
- Export JSON includes the previous version (`project.previousVersion`) exactly as stored. Importing such a file stores it as the new project's snapshot without repairing it; it is repaired only if it is restored. Files without it import as before.

Link recalculation (`recalculateStoredIdentityGraph`, run after a source edit or reparse) rebuilds links from each record's stored neighbors and never rereads source text, so curated neighbors survive and editing one household cannot change another.

No project is treated specially: the old Marano-only load-time migrations were removed. When a project is opened, the Visualizer applies only changes that lose nothing: ids converted with every link kept, and member source lines restored.

## Person Identity

- A household entry is the primary identity boundary. Its first listed person is the household head and uses the household ID.
- Other listed people receive stable member IDs scoped to that household and their recorded position.
- Landholdings use the owning household head's ID, never a name-only key.
- The Landholdings view and the Adjacent Evidence report read English land clauses by different rules, on purpose (decision D13). Italian clauses use the parser's `isItalianLandholdingSentence` and `parseItalianLandholding` in both. The test "the Landholdings view and relation evidence keep their own land-clause rules" in `index-app.test.mjs` pins the differences:
  - **The view draws parcels.** A sentence must name land (`landholding`, `portion`, `plot`, `territory`, `arable`, `garden`, `vineyard`, `grove`, `land`, `property` but not "the property of", …) and say what borders it (`bordering`, `borders`, `adjacent to`, `next to`, `contiguous to`, `confining with`), so a mill bordering someone is not drawn. Words in an editor's brackets do not count. The house the owner lives in is not a parcel, as the Italian "Possiede la casa ove abita" is not, but a residence sentence that mentions a garden or vineyard is drawn as that garden. Since parser version 10 this rule counts the same parcels in a translation as `isItalianLandholdingSentence` does in the Italian; the test "the Landholdings view counts the same parcels in a translation as in the Italian" pins it. Public roads and other public anchors are kept as the parcel's boundary features, and names are kept as written, the owner's own included.
  - **The report collects evidence.** Any owned thing that borders someone counts, so the mill's neighbor is evidence. Sentences about where the household lives (`lives`, `resides`, `dwells`, `inhabits`) are skipped, because residence neighbors are counted separately. Public anchors and the household head's own name are dropped.
- Same-name household heads remain separate. Patronymics are the preferred visible qualifier, followed by age, spouse, and source position.
- References with multiple plausible household heads retain candidate IDs and remain unresolved unless reciprocal, district, or shared-neighbor evidence identifies one candidate uniquely. Shared-neighbor triangulation is limited to the same relationship type and stores its score, confidence, method, and evidence for review.
